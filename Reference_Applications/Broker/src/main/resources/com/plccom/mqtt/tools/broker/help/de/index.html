Wofuer ist dieses Tool gedacht?

Das Broker Tool ist eine grafische Referenzanwendung fuer den PLCcom MQTT Broker. Es hilft beim manuellen Testen von TCP, TLS, WebSocket, WSS, Zertifikatsvertrauen, Zugriffskontrolle und Admin-Daten.

Das Tool ist bewusst auf die sichtbare Broker-Referenzoberflaeche reduziert. Embedded Publishing und lokale Java-Listener werden in den nummerierten Workshops gezeigt.

Listener verwalten

Ein Listener ist ein Netzwerk-Einstiegspunkt des Brokers. Die Tabelle kann beliebig viele TCP-, TLS-, WebSocket- und WSS-Listener enthalten. Jeder Eintrag zeigt Name, Transport, Bind-Adresse, Port, den daraus gebildeten Endpoint sowie fuer TLS/WSS das Zertifikat und den Client-Zertifikatsmodus. Alle Eigenschaften werden im Listener-Editor bearbeitet (Doppelklick oder Bearbeiten).

TransportBedeutungTypischer Port
TCPMQTT ueber TCP ohne TLS.1883
TLSMQTT ueber TLS mit Broker-Zertifikat.8883
WSMQTT ueber WebSocket ohne TLS.8080
WSSMQTT ueber sicheren WebSocket.8443
Neue Listener erhalten automatisch einen eindeutigen Namen. Wenn ein Listener geloescht wird, sucht das Tool beim naechsten Hinzufuegen die naechste freie Nummer.

Bind-Adresse: 127.0.0.1 beschraenkt den Broker auf den lokalen Rechner. 0.0.0.0 lauscht auf allen IPv4-Netzwerkadressen und sollte nur bewusst verwendet werden.

Endpoint: Diese Spalte zeigt die Adresse, die ein Client verwenden kann, zum Beispiel mqtt://127.0.0.1:1883, mqtts://127.0.0.1:8883, ws://127.0.0.1:8080/mqtt oder wss://127.0.0.1:8443/mqtt. Bei WS/WSS laesst sich der WebSocket-Pfad (Standard /mqtt) im Listener-Editor anpassen.

Zertifikat und Zertifikatspasswort: TCP und WS benoetigen kein Serverzertifikat. Jeder TLS/WSS-Listener verwendet entweder Standard oder ein bestimmtes eigenes Zertifikat aus dem Broker-PKI-Store unter pki/own - inklusive eigenem Zertifikatspasswort. Standard bedeutet: Das vom Tool verwaltete Broker-Zertifikat wird automatisch erzeugt oder erneuert, damit seine Subject Alternative Names zu den Hosts der Standard-Listener passen. Ein konkreter Alias bedeutet: Genau dieses Zertifikat wird unveraendert fuer diesen Listener verwendet; das Tool schreibt keine SAN-Werte um und ersetzt es nicht, meldet aber eine Warnung, wenn es nicht zum Endpoint-Host passt. Das Passwort gehoert zur Listener-/Zertifikatszuweisung; es gibt kein gemeinsames Passwort fuer alle Zertifikate.

Client-Zertifikate: Der Modus NONE/OPTIONAL/REQUIRED wird ebenfalls pro Listener gesetzt. Ein Broker kann also gleichzeitig einen TLS-Port mit OPTIONAL und einen zweiten mit REQUIRED betreiben.

TLS, WSS und Zertifikate

TLS und WSS verwenden die eigene Broker-Tool-Identitaet aus dem festen Broker-PKI-Store unter PLCcom/Mqtt/Broker/pki. Fehlt die Identitaet oder deckt sie die Hostnamen der Standard-Listener nicht mehr ab, erzeugt oder erneuert die Library sie automatisch. Die Standard-Identitaet wird dabei einmalig erstellt und danach bei jedem Start wiederverwendet; sie wird nur erneuert, wenn ein Listener-Host noch nicht in ihrem SAN enthalten ist. Ein Client muss dem Broker-Zertifikat daher nicht nach jedem Neustart erneut vertrauen. Wird im Listener-Editor ein anderer Alias gewaehlt, verwendet nur dieser Listener dieses Zertifikat; alle anderen sicheren Listener bleiben beim Standard. Die Sicherheitsregeln fuer Client-Zertifikate und PKI-Vertrauen werden dadurch nicht abgeschaltet.

Der Button Zertifikate oeffnet die lokale Zertifikatsverwaltung. Dort sehen Sie eigenes Zertifikat, trusted Zertifikate, rejected Zertifikate und Issuer.

Client-Zertifikatsmodus pro Listener

Im Listener-Editor legt das Feld Client-Zertifikate pro TLS/WSS-Listener fest, wie der TLS-Handshake mit Client-Zertifikaten umgeht:

ModusVerhalten im TLS-Handshake
NONEEs wird kein Client-Zertifikat angefordert.
OPTIONALEin Client-Zertifikat wird angefordert; Verbindungen ohne Zertifikat werden trotzdem akzeptiert. Der Access Validator kann dann beim MQTT CONNECT gezielt ablehnen.
REQUIREDOhne Client-Zertifikat scheitert bereits der TLS-Handshake - noch vor MQTT CONNECT. Richtig fuer harte mTLS-Ports.

Unbekannte Client-Zertifikate werden im Broker-PKI-Store unter rejected/certs abgelegt und koennen anschliessend vertraut werden. Ein Zertifikat in trusted gilt nur fuer sich selbst, auch wenn es eine CA ist. Soll eine CA fuer die von ihr ausgestellten Client-Zertifikate buergen, gehoert sie nach issuer.

Wichtig: Der PKI-Store beantwortet nur die technische Frage, ob ein Zertifikat vertraut ist. Die fachliche Anmeldung eines Benutzers geschieht danach im Access Validator, der Subject, Issuer, Seriennummer und Fingerprint auswerten kann. Die Access-Regel Benutzerzertifikat verlangen ist deshalb nicht dasselbe wie der TLS-Modus REQUIRED.

Wenn der Client-Zertifikatsmodus REQUIRED ist und der Client kein Zertifikat sendet, bricht der TLS-Handshake ab. Das ist korrektes Verhalten.

Access Validator

Der Access Validator prueft fachliche Zugriffsregeln nach dem MQTT CONNECT sowie bei jedem Publish und Subscribe. Standardmaessig sind alle Regeln aus: Dann wird kein Access Validator installiert und der Broker ist offen. Sobald mindestens eine Regel aktiv ist, wird der Zugriff geprueft.

Benutzername verlangenCONNECT ohne Benutzername wird mit MQTT Reason Code 0x86 (Bad User Name or Password) abgelehnt. Enthaelt die Benutzerliste Eintraege, muessen Benutzername und Passwort exakt zu einem Eintrag passen; bei leerer Liste genuegt ein vorhandener Benutzername.
BenutzerTragen Sie einen Benutzer pro Zeile im Format user=password ein. Leere Zeilen und Zeilen mit # am Anfang werden ignoriert. Die Liste wird nur verwendet, solange Benutzername verlangen aktiv ist - eine gespeicherte Liste blockiert sonst keine Verbindung.
Benutzerzertifikat verlangenCONNECT ohne TLS-Client-Zertifikat wird mit MQTT Reason Code 0x87 (Not authorized) abgelehnt. Das ist eine Access-Regel, keine TLS-Einstellung: Bei Listenern mit Client-Zertifikatsmodus NONE fordert das Tool das Zertifikat intern optional an, damit der Broker sauber beim CONNECT ablehnen kann statt hart im TLS-Handshake zu scheitern.
Blockierter Topic-PrefixPublish und Subscribe auf Topics mit diesem Prefix werden mit 0x87 abgelehnt; die Verbindung bleibt bestehen. QoS-1/2-Publishes erhalten den Fehlercode im PUBACK/PUBREC, QoS-0-Publishes werden verworfen (dort sieht der Client protokollbedingt keinen Fehler). Subscribe erhaelt den Fehlercode im SUBACK.

Die konfigurierte Benutzerliste wird verschluesselt in den Tool-Einstellungen gespeichert; Passwoerter werden niemals ins Log geschrieben. Produktiv wuerde eine Anwendung einen eigenen Access Validator verwenden. Dort koennen Benutzername, Fingerprint, Subject, Issuer, Seriennummer oder eigene Zertifikatserweiterungen auf echte Benutzerkonten und Topic-Rechte gemappt werden. Der PKI-Store ersetzt diese Benutzer- und Rechteverwaltung nicht.

Admin und Statistik

Der Reiter Admin/Statistik zeigt den aktuellen Brokerzustand: gebundene Ports, aktive Verbindungen, Sessions, Subscriptions, queued Messages, retained Messages und Zaehler fuer eingegangene Publishes.

Statistik aktualisieren liest die Werte neu ein. Counter zuruecksetzen setzt Diagnosezaehler zurueck, damit ein neuer Testlauf klar erkennbar ist.

Log und Diagnose

Das Log zeigt Start/Stop, belegte Ports, Zertifikatsereignisse, Access-Entscheidungen, Admin-Aktionen und interne Diagnosemeldungen. Bei Fehlern steht die technische Ursache in der Zeile Details.

Der Diagnose-Level (unten links) steuert das gesamte Log — Broker-Diagnosemeldungen und die Meldungen des Tools: Debug fuer detaillierte Fehlersuche, Info als normaler Standard, Warnings/Errors reduzieren die Ausgabe auf Probleme, Fatal zeigt nur fatale Broker-Fehler und Off blendet alles aus. Abgelehnte CONNECT-Versuche durch den Access Validator, zum Beispiel bei falschem Benutzer oder Passwort, erscheinen als Warning; Passwortdaten werden nie protokolliert. Eine Aenderung des Levels wirkt sofort auf einen laufenden Broker — ohne Neustart.

Nachrichten-Payloads bei Debug. Auf der Stufe Debug erscheint zu jeder an den Broker gesendeten Nachricht ein Diagnoseeintrag mit dem genauen Inhalt — als Text, oder als Hex bei Binaerdaten, auf eine Zeile gekuerzt. Das hilft bei der Analyse; beachten Sie aber, dass Payloads sensible Daten enthalten koennen — lassen Sie Debug daher nur bei Bedarf eingeschaltet.

Grosses Log-Fenster. Das Fenster-Symbol in der Log-Leiste oeffnet das Log in einer separaten, groessenveraenderbaren Live-Ansicht. Der Schalter Auto-Scroll laesst Sie entweder den neuesten Zeilen folgen oder Ihre Position halten, waehrend Sie aeltere Ausgaben lesen. Max. Zeilen begrenzt das gespeicherte Log (die aeltesten Zeilen fallen weg), damit lange Test-Sitzungen fluessig bleiben.

Die Log-Buttons links kopieren, speichern oder leeren die Ausgabe. Fuer Supportfaelle ist der kopierte Log oft aussagekraeftiger als ein Screenshot.
