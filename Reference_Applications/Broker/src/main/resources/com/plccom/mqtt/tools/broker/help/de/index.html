Inhalt Zweck Listener TLS und PKI Access Validator Admin/Statistik Log und Diagnose Fehlerbilder

Wofuer ist dieses Tool gedacht?

Das Broker Tool ist eine grafische Referenzanwendung fuer den PLCcom MQTT Broker. Es hilft beim manuellen Testen von TCP, TLS, WebSocket, WSS, Zertifikatsvertrauen, Zugriffskontrolle und Admin-Daten.

Das Tool ist bewusst auf die sichtbare Broker-Referenzoberflaeche reduziert. Embedded Publishing und lokale Java-Listener werden in den nummerierten Workshops gezeigt.

Listener verwalten

Ein Listener ist ein Netzwerk-Einstiegspunkt des Brokers. Die Tabelle kann beliebig viele TCP-, TLS-, WebSocket- und WSS-Listener enthalten. Jeder Eintrag hat Name, Transport, Bind-Adresse, Port, den daraus gebildeten Endpoint und die Zertifikatsauswahl fuer TLS/WSS.

TransportBedeutungTypischer Port
TCPMQTT ueber TCP ohne TLS.1883
TLSMQTT ueber TLS mit Broker-Zertifikat.8883
WSMQTT ueber WebSocket ohne TLS.8080
WSSMQTT ueber sicheren WebSocket.8443
Neue Listener erhalten automatisch einen eindeutigen Namen. Wenn ein Listener geloescht wird, sucht das Tool beim naechsten Hinzufuegen die naechste freie Nummer.

Bind-Adresse: 127.0.0.1 beschraenkt den Broker auf den lokalen Rechner. 0.0.0.0 lauscht auf allen IPv4-Netzwerkadressen und sollte nur bewusst verwendet werden.

Endpoint: Diese Spalte zeigt die Adresse, die ein Client verwenden kann, zum Beispiel mqtt://127.0.0.1:1883, mqtts://127.0.0.1:8883, ws://127.0.0.1:8080/mqtt oder wss://127.0.0.1:8443/mqtt.

Zertifikat: TCP und WS benoetigen kein Serverzertifikat. TLS und WSS verwenden entweder Standard oder ein bestimmtes eigenes Zertifikat aus dem Broker-PKI-Store unter pki/own. So kann ein bestimmter Port ein eigenes Zertifikat bekommen, waehrend alle anderen TLS/WSS-Ports weiterhin das Standardzertifikat nutzen. Client-Zertifikatsmodus, PKI-Vertrauen, TLS-Protokolle und Timeouts bleiben dabei aus der Standard-TLS-Konfiguration erhalten.

TLS, WSS und Zertifikate

TLS und WSS verwenden die eigene Broker-Tool-Identitaet aus dem festen Broker-PKI-Store unter PLCcom/Mqtt/Broker/pki. Fehlt die Identitaet, erzeugt die Library sie automatisch. Wenn in der Listener-Tabelle fuer einen TLS/WSS-Port ein anderer Alias gewaehlt wird, verwendet nur dieser Port dieses Zertifikat; alle anderen sicheren Listener bleiben beim Standard. Die Sicherheitsregeln fuer Client-Zertifikate und PKI-Vertrauen werden dadurch nicht abgeschaltet.

Der Button Zertifikate oeffnet die lokale Zertifikatsverwaltung. Dort sehen Sie eigenes Zertifikat, trusted Zertifikate, rejected Zertifikate und Issuer.

Client-Zertifikate

Im Feld Client-Zertifikate legen Sie fest, ob der Broker keine, optionale oder verpflichtende Client-Zertifikate erwartet. Unbekannte Client-Zertifikate werden im Broker-PKI-Store unter rejected/certs abgelegt und koennen anschliessend vertraut werden.

Wichtig: Der PKI-Store beantwortet nur die technische Frage, ob ein Zertifikat vertraut ist. Die fachliche Anmeldung eines Benutzers geschieht danach im Access Validator, der Subject, Issuer, Seriennummer und Fingerprint auswerten kann.

Wenn Client-Zertifikate verpflichtend sind und der Client keines sendet, bricht der TLS-Handshake ab. Das ist korrektes Verhalten.

Access Validator

Der Demo-Validator ist ein Testwerkzeug fuer die Oberflaeche. Ohne aktivierten Demo-Validator ist der Broker offen. Mit Demo-Validator koennen Sie Benutzername verlangen, ein vertrauenswuerdiges Benutzerzertifikat verlangen und Publish/Subscribe fuer einen Topic-Prefix blockieren.

Benutzername verlangenCONNECT wird nur akzeptiert, wenn ein Benutzername mitgesendet wird.
Benutzerzertifikat verlangenCONNECT wird nur akzeptiert, wenn der Client ueber TLS/WSS ein vertrautes Zertifikat sendet. Das Zertifikat ist dann die Benutzeridentitaet fuer diesen Test. Steht der TLS-Modus noch auf NONE, fordert das Tool beim Start trotzdem verpflichtend ein Client-Zertifikat an, damit die Regel technisch funktionieren kann.
Blockierter Topic-PrefixPublish und Subscribe auf diesen Prefix werden abgelehnt.

Produktiv wuerde eine Anwendung einen eigenen Access Validator verwenden. Dort koennen Fingerprint, Subject, Issuer, Seriennummer oder eigene Zertifikatserweiterungen auf echte Benutzerkonten und Topic-Rechte gemappt werden. Der PKI-Store ersetzt diese Benutzer- und Rechteverwaltung nicht.

Admin und Statistik

Der Reiter Admin/Statistik zeigt den aktuellen Brokerzustand: gebundene Ports, aktive Verbindungen, Sessions, Subscriptions, queued Messages, retained Messages und Zaehler fuer eingegangene Publishes.

Statistik aktualisieren liest die Werte neu ein. Counter zuruecksetzen setzt Diagnosezaehler zurueck, damit ein neuer Testlauf klar erkennbar ist.

Log und Diagnose

Das Log zeigt Start/Stop, belegte Ports, Zertifikatsereignisse, Access-Entscheidungen, Admin-Aktionen und interne Diagnosemeldungen. Bei Fehlern steht die technische Ursache in der Zeile Details.

Der Diagnose-Level legt fest, ab welcher Schwere Diagnoseereignisse im Tool landen. Abgelehnte CONNECT-Versuche durch den Access Validator, zum Beispiel bei falschem Benutzer oder Passwort, erscheinen als Warning. Passwortdaten werden nicht protokolliert.

Die Log-Buttons links kopieren, speichern oder leeren die Ausgabe. Fuer Supportfaelle ist der kopierte Log oft aussagekraeftiger als ein Screenshot.
