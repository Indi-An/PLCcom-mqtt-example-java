What is this tool for?

The Broker Tool is a graphical reference application for the PLCcom MQTT broker. It helps with manual tests for TCP, TLS, WebSocket, WSS, certificate trust, access control and admin data.

The tool intentionally focuses on the visible broker reference surface. Embedded publishing and local Java listeners are demonstrated in the numbered workshops.

Manage listeners

A listener is a network entry point of the broker. The table can contain any combination of TCP, TLS, WebSocket and WSS listeners. Each entry shows name, transport, bind address, port, the resulting endpoint and - for TLS/WSS - the certificate and the client-certificate mode. All properties are edited in the listener editor (double-click or Edit).

TransportMeaningTypical port
TCPMQTT over TCP without TLS.1883
TLSMQTT over TLS with broker certificate.8883
WSMQTT over WebSocket without TLS.8080
WSSMQTT over secure WebSocket.8443
New listeners receive unique names automatically. After deleting a listener, the next add action searches the next free number.

Bind address: 127.0.0.1 restricts the broker to the local machine. 0.0.0.0 listens on all IPv4 network addresses and should be used deliberately.

Endpoint: This column shows the client address, for example mqtt://127.0.0.1:1883, mqtts://127.0.0.1:8883, ws://127.0.0.1:8080/mqtt or wss://127.0.0.1:8443/mqtt. For WS/WSS the WebSocket path (default /mqtt) can be changed in the listener editor.

Certificate and certificate password: TCP and WS do not need a server certificate. Each TLS/WSS listener uses either Default or a specific own certificate from the broker PKI store below pki/own - including its own certificate password. Default means the tool-managed broker certificate is automatically created or renewed so its Subject Alternative Names cover the configured default-listener hosts. A specific alias means exactly that certificate is used unchanged for this listener; the tool does not rewrite its SAN values or replace it, but it logs a warning when the certificate does not match the endpoint host. The password belongs to the listener/certificate assignment; there is no single password for all certificates.

Client certificates: the NONE/OPTIONAL/REQUIRED mode is also configured per listener. One broker can therefore run one TLS port with OPTIONAL and a second one with REQUIRED at the same time.

TLS, WSS and certificates

TLS and WSS use the broker tool identity from the fixed broker PKI store below PLCcom/Mqtt/Broker/pki. If the default identity is missing, or if it no longer covers the host names of the TLS/WSS listeners that use Default, the library creates or renews it automatically. The default identity is created once and then reused on every start - it is renewed only when a listener host is not yet covered by its SAN, so a client does not have to trust a new broker certificate after each restart. If a different alias is selected in the listener editor, only that listener uses that certificate; all other secure listeners keep the default identity. Explicit listener certificates are never rewritten or silently replaced. This does not disable the configured client-certificate and PKI trust policy.

Standard TLS clients additionally check whether the endpoint host, for example my_broker_host in mqtts://my_broker_host:8883, is present in the broker certificate SAN/CN. A PLCcom client that uses its PKI folder decides by the folder alone and does not match the host name. Client certificates used for mTLS identify the client and are checked for trust and access rules; they are not matched against the broker host name.

The Certificates button opens local certificate management for own certificate, trusted certificates, rejected certificates and issuer certificates.

Client-certificate mode per listener

In the listener editor, the Client certificates field controls per TLS/WSS listener how the TLS handshake treats client certificates:

ModeTLS handshake behavior
NONENo client certificate is requested.
OPTIONALA client certificate is requested; connections without one are still accepted. The access validator can then deny cleanly at MQTT CONNECT.
REQUIREDWithout a client certificate the TLS handshake already fails - before MQTT CONNECT. Correct for strict mTLS ports.

Unknown client certificates are stored below rejected/certs and can then be trusted. A certificate in trusted stands only for itself, even when it is a CA. A CA that should vouch for the client certificates it issued belongs in issuer.

Important: the PKI store answers only the technical trust question. User login is an access-validator decision that can evaluate subject, issuer, serial number and fingerprint after TLS has accepted the certificate. The access rule Require user certificate is therefore not the same as the TLS mode REQUIRED.

If the client-certificate mode is REQUIRED and the client does not send a certificate, the TLS handshake fails. That is expected behavior.

Access validator

The access validator checks business-level access rules after MQTT CONNECT and for every publish and subscribe. By default all rules are off: then no access validator is installed and the broker is open. As soon as at least one rule is active, access is checked.

Require user nameCONNECT without a user name is denied with MQTT reason code 0x86 (Bad User Name or Password). When the users list contains entries, user name and password must match exactly one entry; with an empty list a present user name is sufficient.
UsersEnter one account per line using user=password. Empty lines and lines starting with # are ignored. The list is only used while Require user name is active - a stored list never blocks connections otherwise.
Require user certificateCONNECT without a TLS client certificate is denied with MQTT reason code 0x87 (Not authorized). This is an access rule, not a TLS setting: on listeners with client-certificate mode NONE the tool requests the certificate optionally so the broker can deny cleanly at CONNECT instead of failing the TLS handshake.
Blocked topic prefixPublish and subscribe on topics starting with this prefix are denied with 0x87 while the connection stays open. QoS 1/2 publishes receive the error code in PUBACK/PUBREC, QoS 0 publishes are dropped (the protocol offers no error feedback there). Subscribe receives the error code in SUBACK.

The configured user list is saved encrypted in the tool settings and passwords are never written to the log. A production application would provide its own access validator. It can map user names, fingerprints, subjects, issuers, serial numbers or certificate extensions to real accounts and topic permissions. The PKI store does not replace that user and permission database.

Admin and statistics

The Admin/Statistics tab shows broker state: bound ports, active connections, sessions, subscriptions, queued messages, retained messages and publish counters.

Refresh statistics reads the values again. Reset counters resets diagnostic counters so a new test run is easy to see.

Log and diagnostics

The log shows start/stop, occupied ports, certificate events, access decisions, admin actions and diagnostic messages. For failures, the technical root cause is shown in the Details line.

The Diagnostic level (bottom left) controls the whole log — broker diagnostic events and the tool messages: Debug for detailed troubleshooting, Info as the normal default, Warnings/Errors reduce the output to problems, Fatal shows only fatal broker failures and Off hides everything. CONNECT attempts rejected by the access validator, for example because of a wrong user name or password, are shown as Warning; password data is never logged. Changing the level takes effect immediately on a running broker — no restart needed.

Message payloads at Debug. At the Debug level a diagnostic entry shows the exact content of every message published to the broker — as text, or as hex for binary data, truncated to a single line. This is handy for analysis, but remember that payloads can contain sensitive data, so keep Debug off unless you need it.

Large log window. The window icon in the log toolbar opens the log in a separate, resizable live view. Its Auto-scroll switch lets you either follow the newest lines or hold your position while you read older output. Max. lines caps the retained log (the oldest lines are dropped) so long test sessions stay responsive.

The log buttons copy, save or clear the output. For support, copied logs are often more useful than screenshots.
