What is this tool for?

The Broker Tool is a graphical reference application for the PLCcom MQTT broker. It helps with manual tests for TCP, TLS, WebSocket, WSS, certificate trust, access control and admin data.

The tool intentionally focuses on the visible broker reference surface. Embedded publishing and local Java listeners are demonstrated in the numbered workshops.

Manage listeners

A listener is a network entry point of the broker. The table can contain any combination of TCP, TLS, WebSocket and WSS listeners. Each entry has a name, transport, bind address, port, the resulting endpoint and the TLS/WSS certificate selection.

TransportMeaningTypical port
TCPMQTT over TCP without TLS.1883
TLSMQTT over TLS with broker certificate.8883
WSMQTT over WebSocket without TLS.8080
WSSMQTT over secure WebSocket.8443
New listeners receive unique names automatically. After deleting a listener, the next add action searches the next free number.

Bind address: 127.0.0.1 restricts the broker to the local machine. 0.0.0.0 listens on all IPv4 network addresses and should be used deliberately.

Endpoint: This column shows the client address, for example mqtt://127.0.0.1:1883, mqtts://127.0.0.1:8883, ws://127.0.0.1:8080/mqtt or wss://127.0.0.1:8443/mqtt.

Certificate: TCP and WS do not need a server certificate. TLS and WSS use either Default or a specific own certificate from the broker PKI store below pki/own. This lets one port present a dedicated certificate while all other secure listeners continue to use the default certificate. The client-certificate mode, PKI trust handling, TLS protocols and timeouts still come from the default TLS configuration.

TLS, WSS and certificates

TLS and WSS use the broker tool identity from the fixed broker PKI store below PLCcom/Mqtt/Broker/pki. If the identity is missing, the library creates it automatically. If a different alias is selected for a TLS/WSS row, only that port uses that certificate; all other secure listeners keep the default identity. This does not disable the configured client-certificate and PKI trust policy.

The Certificates button opens local certificate management for own certificate, trusted certificates, rejected certificates and issuers.

Client certificates

The Client certificates field controls whether the broker ignores, optionally accepts or requires client certificates. Unknown client certificates are stored below rejected/certs and can then be trusted.

Important: the PKI store answers only the technical trust question. User login is an access-validator decision that can evaluate subject, issuer, serial number and fingerprint after TLS has accepted the certificate.

If client certificates are required and the client does not send one, the TLS handshake fails. That is expected behavior.

Access validator

The demo validator is a test feature for the UI. Without it, the broker is open. With it, you can require a user name, require a trusted user certificate and deny publish/subscribe for a topic prefix.

Require user nameCONNECT is accepted only when a user name is sent.
Require user certificateCONNECT is accepted only when the client sends a trusted certificate over TLS/WSS. That certificate is the user identity for this test. If the TLS mode is still NONE, the tool still requires a client certificate at broker startup so the rule can work technically.
Blocked topic prefixPublish and subscribe are rejected for this prefix.

A production application would provide its own access validator. It can map fingerprint, subject, issuer, serial number or certificate extensions to real user accounts and topic permissions. The PKI store does not replace that user and permission database.

Admin and statistics

The Admin/Statistics tab shows broker state: bound ports, active connections, sessions, subscriptions, queued messages, retained messages and publish counters.

Refresh statistics reads the values again. Reset counters resets diagnostic counters so a new test run is easy to see.

Log and diagnostics

The log shows start/stop, occupied ports, certificate events, access decisions, admin actions and diagnostic messages. For failures, the technical root cause is shown in the Details line.

The Diagnostic level controls the minimum severity that reaches the tool. CONNECT attempts rejected by the access validator, for example because of a wrong user name or password, are shown as Warning. Password data is not logged.

The log buttons copy, save or clear the output. For support, copied logs are often more useful than screenshots.
