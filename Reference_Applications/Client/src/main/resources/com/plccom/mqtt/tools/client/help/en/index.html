What is this tool for?

The Client Tool is a graphical reference application for the PLCcom MQTT high-level client. It is a quick place to try connections, publishing, subscriptions, QoS, retained messages, MQTT 5 properties and diagnostics.

Inputs are stored in the PLCcom MQTT user profile. Sensitive values such as license data, MQTT password and certificate password are not stored as plain text.

Connect

  1. Enter license data if required.
  2. Enter an endpoint, for example mqtt://127.0.0.1:1883.
  3. Keep protocol AUTO unless you intentionally test MQTT 5.0 or MQTT 3.1.1.
  4. Put user name and password into the separate fields, not into the URI.
  5. Click Connect.

Endpoint assistant

The small ... button opens an assistant for transport, host, port and optional WebSocket path. It writes the resulting URI back into the single endpoint field.

SchemeMeaningTypical port
mqtt://MQTT over TCP without TLS.1883
mqtts://MQTT over TLS.8883
ws://MQTT over WebSocket without TLS.8080
wss://MQTT over secure WebSocket.8443
TCP/TLS endpoints must not contain a WebSocket path. Use ws:// or wss:// for paths such as /mqtt.

TLS and certificates

For mqtts:// and wss://, the tool validates the broker certificate through the fixed client PKI store below PLCcom/Mqtt/Client/pki. Unknown certificates are placed into rejected/certs and can be reviewed through Certificates.

If the broker requires a client certificate, enable Send TLS client certificate. The tool then uses its own identity from pki/own. If it is missing, the library creates it automatically.

After trusting a certificate, start the connection again. The first attempt remains rejected for safety.

Last Will / Testament

The MQTT Last Will Testament is a message that the client registers with the broker during CONNECT. The broker publishes this message later only when the client disappears unexpectedly, for example because the process was killed, the network failed or power was lost. A normal click on Disconnect intentionally does not publish the testament.

On the Connection tab, enable Enable testament. Use Settings to open the detail fields for topic, payload, QoS, retain and MQTT 5 will options.

FieldMeaningTypical use
Last Will TopicTopic on which the broker publishes the testament.plccom/tool/client/status or a device status topic.
Last Will PayloadPayload of the testament message.offline, disconnected unexpectedly or a small JSON status object.
Last Will QoSDelivery quality for the testament message.QoS 1 is a good default for status messages.
RetainThe broker stores the testament as latest known state.Very useful for online/offline state so new subscribers immediately see the state.
Will DelayMQTT 5 wait time in seconds before the broker publishes the testament.Useful for short network interruptions that recover quickly.
Will ExpiryMQTT 5 expiry time for the testament message.For status values that should no longer be shown after a certain time.
Content TypeMQTT 5 hint for the testament payload format.text/plain or application/json.
Practical test: subscribe a second client to the Last Will topic, enable the testament, connect and then terminate the client process hard. The second client should receive the testament message.

Publish basics

The Publish tab sends a payload to exactly one topic. A Topic Name is the address of the message, for example plccom/test/temperature. Wildcards such as # and + are not allowed when publishing.

QoS 0Send once without acknowledgement. Fast, but not guaranteed.
QoS 1At least once. The broker acknowledges; duplicates are possible.
QoS 2Exactly once. Safest exchange, but more protocol steps.
RetainThe broker stores the last value for this topic and replays it immediately to new subscribers.

For simple tests, Topic Name, Payload, QoS and optionally Retain are enough. The right side contains optional MQTT 5 metadata.

Publish MQTT 5 fields

The fields on the right side of the Publish tab are optional. Leave them empty for a normal message. They become useful when you test MQTT 5 metadata, request/response patterns or extra message information.

FieldWhat does it mean?When to use it?Example
Content TypeDescribes the payload format. It is a hint for the receiver, similar to HTTP.Use it when receivers should know whether the payload is text, JSON, XML or another format. Brokers usually forward it without interpreting it.text/plain, application/json. Important: this is not a topic. A value such as bad/#topic is semantically wrong, even if it would only be transported as text.
Message Expiry (s, 0=off)Lifetime of the message in seconds. After expiry, the broker should no longer deliver it.Useful for measurements, status values or commands that are worthless after a short time. With 0, the tool sends no expiry value.30 for a value that is valid for 30 seconds. 0 for normal tests.
MQTT 5 Response TopicTopic where a receiver should publish its answer. MQTT request/response is a convention, not a separate packet type.Use it when you publish a request and expect a response. The receiver must read this field and publish the answer to that topic.reply/plccom-client-1. Leave empty for normal publish tests. Wildcards are not useful here.
MQTT 5 Correlation DataAn opaque correlation value. The receiver should copy it into the response.Use it together with Response Topic so parallel requests can be matched to the correct answer.request-4711. Leave empty when not testing request/response.
Name and ValueOne MQTT 5 User Property as a key/value pair. This is extra metadata on the message.Use it for harmless additional information such as source, unit, tenant or test case. Do not use it for passwords or secrets.Name unit, value degC; name source, value client-tool. It is sent only when both fields are filled.
Rule of thumb: Topic and Payload carry the actual message. The MQTT 5 fields on the right only describe the message further or help with request/response.

Subscribe basics

The Subscribe tab subscribes to Topic Filters. A Topic Filter may contain wildcards. plccom/test/# receives all messages below plccom/test/.

FieldMeaningTypical setting
Topic FilterWhich topics the client wants to receive. # and + are allowed here.plccom/test/# for many tests, or a concrete topic for a focused test.
Max. QoSThe highest QoS level with which this client wants to receive messages for this subscription.Usually QoS 1. Use QoS 2 only when you explicitly test that flow.
Receive TimeoutWait time for Receive once. The tool gives up if no matching message arrives in time.1000 to 10000 ms, depending on your test environment.

Subscribe MQTT 5 options

These options change how the broker delivers matching messages to this client. For first simple tests, keep them disabled.

OptionWhat does it mean?When to use it?Expected behavior
Shared SubscriptionMultiple clients with the same Share Name share one subscription. The broker distributes matching messages across the group.Use it when several workers should process the same task stream, but each message should be handled by only one worker.Enable it and set a Share Name, for example tool-workers. The tool builds the shared subscription format internally. One client may look unchanged; two clients show the distribution.
No LocalThe client does not receive its own published messages through this subscription.Use it when publish and subscribe run in the same client and echo messages are unwanted.Publish to a subscribed topic. With No Local, that own message should not appear in this client. This option is MQTT 5.
Retain As PublishedThe broker should preserve the Retain flag as it was set by the publisher.Use it when the receiver needs to know whether the publisher marked the message as retained.The displayed Retain=true/false stays closer to the original publish. Without this option, the broker may adjust the flag depending on the delivery situation.
Retain HandlingControls whether retained messages are replayed immediately when subscribing.Use it when you want to control whether a client immediately receives the last known state at startup.Send retained now: replay immediately. Only if new: only if this subscription is new. Do not send retained: do not replay retained messages during subscribe.
Subscription IdentifierAn MQTT 5 number that the broker can attach to matching incoming messages.Use it when one client has many subscriptions and a shared callback needs to know which subscription matched.Enable it and set a number, for example 1. Incoming messages can show this number in their message details if the broker supports it.
Some brokers do not support every MQTT 5 option. If a broker rejects an option, the log shows the corresponding error or reason code.

Request / Response

The Request tab tests the MQTT 5 request/response pattern. MQTT itself has no built-in question/answer; MQTT 5 enables it through two message properties: Response Topic and Correlation Data. You are the requester: you send a request and receive a correlated reply.

A responder (a device or service) subscribes to the request topic, processes the request and publishes the answer to the response topic with the same correlation token. This tool sends the request, waits for the correlated reply and shows it.

FieldMeaningExample
Request TopicTopic on which the request is published. The responder must listen here.request/plccom
Response TopicTopic on which the responder should publish the answer. The tool waits here for the reply.response/plccom/client
PayloadThe request content, for example a command or the name of a value to read.read

Click Send request (only when connected). The tool sends the request with random Correlation Data and waits up to 5 seconds for the matching reply. The reply is written to the log and added to the Messages tab.

Typical use: read a value on demand ("read register X") or send a command and wait for a result/acknowledgement — a lightweight question/answer (RPC) over MQTT without a second protocol.

Messages, log and diagnostics

Received messages appear in the Messages tab and in the log. The log also shows connection state, failures, certificate events and diagnostics.

The Diagnostic level on the connection page controls how much internal detail is shown: Debug for detailed troubleshooting, Info as the normal default, Warnings/Errors/Fatal for reduced output and Off to suppress diagnostic events.

The log buttons copy, save or clear the output. For support, copy the relevant log lines including the root cause.
